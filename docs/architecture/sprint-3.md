## اصلاح قاعده‌ی وابستگی §07 — Data dependency در برابر Module dependency

**تصمیم (مالک، گزینه‌ی ۱):** ماژول `Customers` می‌تواند جدول‌های `orders`، `order_items` و `customer_metrics` را **فقط‌خواندنی و با Query Builder** بخواند. این یک **وابستگی داده** (Data dependency) است، نه **وابستگی ماژول** (Module dependency): جدول وابستگی PRD §07 که برای `Customers` فقط `Core` را می‌دهد **تغییر نمی‌کند** و همچنان درباره‌ی **کد** است. **چرا:** PRD خودش `CustomerProfileService::buildThreeSixty()` را در `Customers` گذاشته و Customer 360 (PRD §18) به سفارش‌ها و متریک‌های یک مشتری نیاز دارد؛ Interface کردن آن از Orders/Metrics یک چرخه می‌سازد چون `Orders → Customers` و `Metrics → Customers` از قبل وجود دارند (§07)، و انتقال صفحه به Metrics مالکیت پروفایل را از ماژول مشتری جدا می‌کرد.

- **مجاز:** `DB::table('orders' | 'order_items' | 'customer_metrics')` با Query Builder و Binding، فقط `SELECT` (بدون هیچ نوشتن، Dispatch یا Log)، برای داده‌ی یک مشتری.
- **ممنوع (همان قواعد قبلی، بدون تغییر):** `use` هر کلاسی از `Orders`، `Metrics` یا هر ماژول دیگر (Model، Service، Enum، Event) جز `Customers\Models\Customer`؛ SQL خام (Rule 7: فقط Metrics/Analytics)؛ خواندن هر جدول دیگر ماژول‌های دیگر (مثلاً `products`، `audit_logs`، `sync_jobs`)؛ محاسبه‌ی معیار در لحظه (معیارها فقط از `customer_metrics` خوانده می‌شوند).
- **اعمال:** `tests/Arch/CustomerShowBoundaryTest.php` همین‌ها را قفل می‌کند: فقط این سه جدول (به‌علاوه `customers`)، بدون `use` کلاس ماژول‌های دیگر، بدون نوشتن، بدون SQL خام. تست‌های سراسری `ArchitectureTest` (جدول وابستگی کلاسی، Model بین‌ماژولی، SQL خام) **دست‌نخورده و سبزند** — چون این استثنا به‌خاطر ماهیت «داده، نه کلاس» هرگز رفتار آن‌ها را تغییر نمی‌دهد.
- **دامنه:** فعلاً فقط `CustomerShowService` (P3-03) از آن استفاده می‌کند. افزودن مصرف‌کننده‌ی دوم یا جدول چهارم یعنی تصمیم تازه و ثبت تازه در همین بخش.

`PRD.md` §07 دست‌نخورده ماند (سند مرجع محصول)؛ این بخش تفسیر پیاده‌سازی آن است و در تناقض با آن، PRD برنده می‌ماند مگر مالک خلافش را بگوید.

## P3-04 — Timeline مشتری با Cursor Pagination (`GET /customers/{customer}/timeline`)

**جدول `customer_events` وجود نداشت و ساخته شد** (`2026_09_20_130000_create_customer_events_table`): `id`، `customer_id` (FK، CASCADE؛ حذف نرم مشتری رویدادها را نگه می‌دارد)، `event_type varchar(50)`، `payload jsonb` (Nullable)، `happened_at` و `created_at` (`timestamptz`)، Index `(customer_id, happened_at DESC, id DESC)`. **تصمیم:** `event_type` مجموعه‌ی بسته است، نه متن آزاد: Enum `CustomerEventType` (`order_placed`، `order_refunded`، `note_added`، `status_changed`) به‌علاوه‌ی CHECK (CLAUDE.md §2/§3: هر ستون Enum-گونه CHECK دارد؛ «مثال» تسک همان چهار مقدار گرفته شد) و نوع تازه یعنی Migration تازه. ⚠ **هیچ چیزی در این Build در `customer_events` نمی‌نویسد** (نه Sync سفارش، نه یادداشت، نه تغییر وضعیت): Timeline روی داده‌ی واقعی تا وجود «نویسنده» خالی است و صفحه در این حالت بخش را **نشان نمی‌دهد** (مثل P3-03). تصمیم بعدی برای مالک: Backfill از `orders` و/یا نوشتن رویداد از `OrderService`/یادداشت‌ها (تسک جدا).

**سرویس و Cursor** (`CustomerTimelineService`، فقط‌خواندنی): ترتیب `happened_at DESC, id DESC`؛ Cursor = Base64 **URL-safe بدون Padding** از `{"happened_at":"<UTC ISO>","id":<int>}` (نیاز به Percent-encoding ندارد)، فقط و فقط در همین سرویس Encode/Decode می‌شود (Arch: نه Controller، نه Request، نه DTO، نه React)، Decode سخت‌گیرانه است (Base64 Strict، دقیقاً همین دو کلید، `id` عدد صحیح ≥ ۱، تاریخ واقعی که بعد از Parse عیناً برگردد، طول ≤ ۲۰۰) و فقط به‌شکل **مقدار Bind‌شده** وارد Query می‌شود؛ Cursor نامعتبر ← ۴۲۲ روی `cursor` پیش از هر Query، و Cursor همیشه داخل `customer_id` همان مشتری می‌ماند (Cursor مشتری دیگر چیزی فاش نمی‌کند، تست‌شده). یک ردیف اضافه خوانده می‌شود تا `has_more` **دقیق** باشد (صفحه‌ی کاملاً پر و بدون بعدی ← `false`). `per_page` پیش‌فرض ۲۰، حداکثر ۵۰ (بیشتر ← ۴۲۲ نه Clamp)؛ `pageFor()` برای Endpoint (مشتری حذف‌شده/ناموجود ← ۴۰۴، ۲ Query) و `page(Customer)` برای فراخوان‌ی که مشتری را قبلاً بارگذاری کرده (۱ Query).

**⚠ یافته‌ی اندازه‌گیری — و اصلاحش:** نسخه‌ی اول شرط Cursor را به‌شکل `OR` بازشده (`happened_at < ? OR (happened_at = ? AND id < ?)`) می‌نوشت؛ EXPLAIN روی داده‌ی مصنوعی (DB تست `heymode_testing`، ۴۳۰٬۰۰۰ رویداد، یک مشتری با ۳۰٬۰۰۰، همه در یک تراکنش Rollback‌شده) نشان داد شرط به‌صورت **Filter** اعمال می‌شود (۱۰٬۰۰۰ ردیف خوانده و دور ریخته، ۶۱۰ Buffer، ۲٫۵ms در عمق ۱۰٬۰۰۰) یعنی هزینه با عمق رشد می‌کرد — همان مشکل Offset. با `whereRowValues(['happened_at','id'], '<', [...])` (همان مقایسه‌ی سطری `(happened_at, id) < (?, ?)` تسک؛ API خود Query Builder است نه SQL خام، پس Rule 7 سالم می‌ماند) شرط **Index Cond** شد: ۵ Buffer، ۰٫۰۵۶ms، و صفحه‌ی ۲۰۰م هم‌هزینه‌ی صفحه‌ی اول. اندازه‌گیری نهایی (سرویس + PHP، p50/p95): صفحه‌ی اول ۳٫۳/۳٫۷ms، `per_page=50` ۵٫۷/۷٫۱ms، ۲۰۰ صفحه عمق ۵٫۷/۶٫۶ms. Arch شکل `whereRowValues` را قفل می‌کند. ⚠ این عددها روی DB **تست** با داده‌ی مصنوعی‌اند؛ روی DB توسعه اندازه‌گیری نشد چون Migration هنوز آن‌جا اجرا نشده.

**Payload و تاریخ:** فقط پنج کلید (`order_id`، `note`، `old_status`، `new_status`، `woo_order_id`) و فقط مقدار Scalar ساده (آرایه‌ی تودرتو نمی‌تواند کلید دیگری را بیرون ببرد)؛ کلیدها به ترتیب Allowlist خارج می‌شوند نه ترتیب ذخیره (JSONB کلیدها را جابه‌جا می‌کند)؛ بدون کلید مجاز ← `payload: null` (نه `{}`). ⚠ `note` متن آزاد است و به هر دارنده‌ی `customers.view` نشان داده می‌شود. هر رویداد `happened_at_jalali` (تاریخ جلالی **به‌همراه ساعت تهران**، ارقام ASCII مثل بقیه‌ی برنامه؛ مثال تسک با ارقام فارسی و بدون ساعت فقط توضیحی بود) و `happened_at_iso` (UTC، `…Z`) دارد و مقدار خام هرگز نمی‌رود (Arch: کلید `happened_at` فقط یک بار، داخل Cursor). **Frontend:** `CustomerTimeline.tsx` (خط عمودی در لبه‌ی Inline-start = راست RTL، آیکون بر اساس نوع با آیکون پیش‌فرض، Load-more با حالت‌های idle/loading/error، Cursor بدون دست‌کاری برگردانده می‌شود، آدرس از Wayfinder، پاسخ با Type-guard بررسی می‌شود)؛ `show.tsx` آن را از Props صفحه می‌گیرد و فقط اگر رویدادی هست نشان می‌دهد (بررسی `Schema::hasTable` در زمان اجرا پیاده نشد: Migration همین تسک جدول را تضمین می‌کند و بررسی، Query اضافه و مسیر مرده می‌بود).

## P3-05 — تب‌های سفارش‌ها/محصولات و یادداشت‌ها در Customer 360

**پنج Route** (همه `auth` + `customers.view`، `whereNumber`): `GET customers/{customer}/orders` (`customers.orders`)، `GET .../products` (`customers.products`)، `GET .../notes` (`customers.notes.index`؛ لازم بود چون بودجه‌ی صفحه‌ی ۳۶۰ با Timeline دقیقاً ۶ است و ۷م نمی‌شد)، `POST .../notes` (`customers.notes.store`) و `DELETE .../notes/{note}` (`customers.notes.destroy`). سرویس‌های `CustomerOrdersService`، `CustomerProductsService`، `CustomerNotesService` (ماژول Customers) و Controllerهای بدون منطق (یک سرویس، JSON/۲۰۱/۲۰۴). هر سه فهرست **Cursor** دارند (`per_page` پیش‌فرض ۲۵، حداکثر ۵۰، بیشتر ← ۴۲۲ نه Clamp؛ Cursor بد ← ۴۲۲؛ مشتری حذف‌نرم/ناموجود ← ۴۰۴؛ بی‌مجوز همیشه ۴۰۳ پیش از ۴۰۴)؛ `total_count` فقط در سفارش‌ها و با `COUNT(*)` جدا. اندازه‌گیری روی DB توسعه (`heymode`، پرسفارش‌ترین مشتری: ۴۵ سفارش، ۵۵ خط آیتم، فقط SELECT): سفارش‌ها ۳ Query، p50 ≈ ۳ms؛ محصولات ۲ Query، p50 ≈ ۲ms؛ صفحه‌ی دوم هم‌هزینه‌ی اول.

## P3-06 — لیست سفارش‌ها و صفحه‌ی جزئیات

**دو Route** (هر دو `auth` + `orders.view`، بدون Soft-delete روی `orders` پس شناسه‌ی ناموجود همیشه ۴۰۴ ساده است): `GET /orders` (`orders.index`، لیست با فیلتر و Offset Pagination) و `GET /orders/{order}` (`orders.show`، جزئیات یک سفارش). سرویس‌ها در ماژول Orders (`OrderListService`، `OrderShowService`) هستند و جدول `customers` را **فقط با Query Builder** می‌خوانند، بدون `use` هیچ کلاسی از Customers — حتی همان یک Model (`Customer`) که CLAUDE.md §1 در همه‌جا مجاز می‌داند؛ این‌جا حتی آن استثنا هم عمداً استفاده نشد تا مرز با تست Arch سخت‌گیرانه‌تر باشد. این همان «Data dependency در برابر Module dependency»ی است که در P3-03 تصویب شد، این‌بار در جهت عکس (Orders جدول Customers را می‌خواند، نه برعکس).

**لیست:** `orders` LEFT JOIN `customers` (فقط برای `display_name`؛ سفارش بدون مشتری با `needs_phone_review=true` هرگز با Join حذف نمی‌شود). فیلترها با AND: `woo_order_id` دقیق، `status` (اعتبارسنجی در برابر مقادیر **واقعاً ذخیره‌شده** در `orders.status` با `Rule::in()`، نه Enum — CLAUDE.md هاردکد وضعیت سفارش را ممنوع می‌کند و PRD صریحاً می‌گوید Enum وضعیت سفارش نسازید)، `is_realized`، **`needs_phone_review`** (فیلتر مخصوص همین لیست؛ فیلتر `needs_review` در P3-01 چیز دیگری است — پرچم `customers.needs_review` روی جدول `customers`، نه `orders.needs_phone_review`) و بازه‌ی روز جلالی روی `ordered_at` با همان `JalaliDay` و قرارداد `[from, to]` P3-01 (شروع Inclusive، پایان Exclusive روی نیمه‌شب روز بعد). ترتیب `ordered_at DESC, id DESC`؛ Offset Pagination ۲۵تایی — برخلاف Cursor صفحه‌های Customer 360 (P3-04/۰۵)، این لیست برای مرور صفحه‌به‌صفحه توسط انسان است نه پیمایش کامل توسط اسکریپت، پس شمارش Offset این‌جا مناسب است. مبلغ **بدون تبدیل** (تومان، دقیقاً همان `total`).

**جزئیات، حداکثر ۳ Query:** Q1 ردیف سفارش، Q2 آیتم‌های همان سفارش، Q3 مشتری **فقط اگر `customer_id` دارد** (رد نمی‌شود، Skip می‌شود). تلفن همیشه Mask است — **برای هر بیننده، حتی دارنده‌ی `customers.view_full_phone`** — و راه کامل‌دیدن فقط `PhoneRevealButton` سمت `orders/show.tsx` است که به Endpoint حسابرسی‌شده‌ی P3-02 می‌زند؛ `needs_phone_review` یک Flag صریح در Response است. `profile_url` با `route('customers.show', $id)` ساخته می‌شود.

**⚠ انحراف آگاهانه از متن تسک:** متن Backend گفته بود «phone_normalized → mask مگر customers.view_full_phone» یعنی نمایش شماره‌ی کامل برای دارنده‌ی این مجوز — این مستقیماً تصمیم بسته‌شده‌ی P3-02 را نقض می‌کرد («لیست همیشه Mask؛ نمایش کامل فقط از راه Endpoint حسابرسی‌شده، یک‌به‌یک»)، درحالی‌که همان تسک در بخش Frontend صریحاً `PhoneRevealButton` را برای همین صفحه خواسته بود — یعنی خود تسک با خودش ناسازگار بود. تصمیم گرفتم با بخش Frontend و با تصمیم بسته‌شده‌ی P3-02 هماهنگ بمانم: DTO همیشه Mask می‌کند، `hasPermission` روی دکمه فقط UX است. این‌جا صراحتاً ثبت می‌شود تا اگر مالک قصد دیگری داشته، بازبینی شود.

**اندازه‌گیری روی DB توسعه** (`heymode`؛ ۲۴٬۵۷۰ سفارش، فقط SELECT): جزئیات سریع است (سفارش با مشتری: ۳ Query، p50 ≈ ۱٫۵ms؛ بدون مشتری: ۲ Query، p50 ≈ ۱ms). **⚠ یافته‌ی Index:** صفحه‌ی اول لیست **بدون فیلتر** کند‌تر است (p50 ≈ ۳۰–۵۵ms، تا ۲۲۴ms در بدترین حالت مشاهده‌شده): `EXPLAIN` نشان می‌دهد `Seq Scan` روی کل جدول (۷۰۶ Buffer) برای مرتب‌سازی `ordered_at DESC, id DESC` — ایندکس‌های موجود (`orders_customer_ordered_at_index`، `orders_realized_ordered_at_index`) هیچ‌کدام با `ordered_at` **به‌تنهایی** (بدون `customer_id`/`is_realized` در جلو) کار نمی‌کنند، و `COUNT(*)` صفحه‌بندی هم روی همین جدول Seq Scan می‌زند. این لیست بدون فیلتر دقیقاً حالت «باز کردن صفحه‌ی سفارش‌ها بدون هیچ فیلتری» است که به‌احتمال زیاد رایج‌ترین بار اول است. **تصمیم من:** بدون اجازه Migration/Index تازه نساختم (خارج از فایل‌های اعلام‌شده‌ی این تسک)؛ ایندکس پیشنهادی `(ordered_at DESC, id DESC)` روی `orders` برای تصمیم مالک ثبت می‌شود.

**تست:** ۵۱ تست خالص جدید (۲۳۲۹ ← ۲۳۸۰ سبز؛ لیست ۱۸، جزئیات ۱۹، Arch ۱۴)، `tests/Arch` ۱۸۱/۱۸۱ (شامل به‌روزرسانی عمدی شمار GET در `CustomerListBoundaryTest`: ۶ ← ۸)، PHPStan ۰ خطا. **Mutation check ۱۰ نقض عمدی همگی گرفته و فایل‌ها برگردانده شد** (OR01: فیلتر `needs_phone_review` حذف ← ۱؛ OR02: Mask حذف از DTO ← ۳؛ OR03: Query اضافه بدون تغییر رفتار ← ۲؛ OR04: سفارش بدون مشتری Throw به‌جای `customer: null` ← ۴؛ به‌علاوه فیلتر `is_realized`/`status`/بازه‌ی تاریخ، مجوز Route، تقسیم مبلغ بر ۱۰، و Scope آیتم‌ها). Migration تازه‌ای لازم نبود.

## P3-07 — لیست محصولات با آمار فروش (پایان Sprint 3)

**یک Route**، `GET /products` (`products.index`)، پشت `auth` + **`catalog,view`** — این Permission وجود نداشت و به `PermissionSeeder` اضافه شد (Owner/Manager/Analyst به‌صورت خودکار می‌گیرند، چون قاعده‌ی موجودشان است؛ Support/Viewer مثل `orders.view` بدون تغییر عمدی نقشه‌ی نقش‌ها نگه داشته شدند). سرویس (`ProductListService`) جدول‌های `order_items`/`orders` را **فقط با Query Builder** می‌خواند و هیچ کلاسی از ماژول Orders را `use` نمی‌کند — حتی استثنای `Customer` که CLAUDE.md همه‌جا مجاز می‌داند این‌جا هم عمداً استفاده نشد؛ همان «Data dependency در برابر Module dependency»ی P3-03/۰۶، این‌بار سمت Catalog.

**⚠ استثنای Rule 7 برای Aggregate فروش Catalog (تصمیم آگاهانه، نه سهوی):** متن تسک ادعا کرده بود «Rule 7 فقط Metrics/Analytics را محدود می‌کند»، اما تست واقعی (`ArchitectureTest::it confines raw SQL...`) فقط همان دو ماژول را Allow‌list می‌کرد — Catalog از قبل مجاز نبود. با این حال SUM/COUNT/MAX گروه‌بندی‌شده در یک ردیف در Laravel Query Builder بدون `selectRaw`/`orderByRaw` امکان‌پذیر نیست، و CLAUDE.md §3 صریح می‌گوید «تحلیل سنگین یک عبارت SQL است، هرگز حلقه‌ی PHP روی ردیف‌ها» — محاسبه‌ی این آمار (روی همه‌ی سفارش‌های Realized کل فروشگاه، نه یک مشتری) با حلقه‌ی PHP دقیقاً همان قاعده را نقض می‌کرد. **تصمیم:** Rule 7 فقط برای یک فایل، `app/Modules/Catalog/Services/ProductListService.php`، Amend شد (`ArchitectureTest`، Allowlist جدا از Prefix ماژول‌ها)؛ بقیه‌ی Catalog همچنان ممنوع است (تست تازه `CatalogBoundaryTest` این را قفل می‌کند) و هر Fragment خام همان فایل باید رشته‌ی ثابت باشد — هیچ `$` یا Concatenation ورودی کاربر در آن راه ندارد (تست می‌سنجد). این دقیقاً هم‌خانواده‌ی انحراف P3-05 برای گروه‌بندی محصولات مشتری است، با این تفاوت که آن‌جا مقیاس کوچک (سفارش‌های یک مشتری) اجازه داد PHP جایگزین SQL شود؛ این‌جا مقیاس کل فروشگاه است و SQL درست‌تر بود.

**Aggregate:** `order_items JOIN orders WHERE orders.is_realized = true GROUP BY product_id` → `total_qty_sold`، `total_revenue`، `order_count` (`COUNT(DISTINCT order_id)`، تا دو خط یک سفارش دوبار شمرده نشود)، `last_sold_at`؛ با `leftJoinSub` روی `products`. محصول بدون فروش (بدون تطبیق LEFT JOIN) در DTO صفر می‌شود (نه Null — صفر واقعیتی است، نه مقدار گم‌شده)، `last_sold_at` همچنان Null (صفحه: «هنوز فروش نداشته»). **SKU:** جدول `products` اصلاً ستون `sku` ندارد (بر خلاف فرض متن تسک) — SKU روی `product_variations` است و هر محصول (Simple یا Variable) دست‌کم یک Variation دارد. SKU نمایشی = پایین‌ترین `id` Variation دارای SKU (برای محصول Simple دقیقاً همان SKU؛ برای Variable فقط یک نماینده است، نه یکتا) با `leftJoinSub`؛ فیلتر SKU دقیق روی **هر** Variation محصول با `whereExists` می‌گردد، نه فقط SKU نماینده. `status` Enum خود Catalog (`ProductStatus`) است، نه رشته‌ی خام Woo مثل وضعیت سفارش — پس اعتبارسنجی با `Rule::enum()` این‌جا مجاز است. ترتیب پیش‌فرض `COALESCE(sales.total_revenue, 0) DESC, products.id DESC` (Postgres پیش‌فرض NULL را در DESC اول می‌گذارد؛ بدون Coalesce محصولات بی‌فروش بالای لیست می‌افتادند).

**Woo Admin Link:** `admin_url` سمت Backend از `config('woo.base_url')` ساخته می‌شود (هرگز در Frontend)، فقط وقتی مقدار دارد، وگرنه Null و صفحه فقط نام را متن ساده نشان می‌دهد.

**تست:** ۳۸ تست خالص جدید (۲۳۸۰ ← ۲۴۱۸ سبز؛ کنترلر ۲۲، `CatalogBoundaryTest` ۱۶) + `ArchitectureTest` Amend‌شده، Arch کل ۱۹۷/۱۹۷ (شمار GET در `CustomerListBoundaryTest`: ۸ ← ۹)، PHPStan ۰ خطا. **Mutation check ۳ نقض عمدی طبق تسک همگی گرفته و فایل‌ها برگردانده شد** (C01: حذف فیلتر `is_realized` از Aggregate؛ C02: ترتیب ASC؛ C03: محصول بدون فروش Null به‌جای صفر).
