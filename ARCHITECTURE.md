## Confirmed decisions

- **`products.sku`/`products.price` (nullable, deviates from PRD §09's literal `products` schema) — project-owner decision, Sprint 6:** PRD §09 defines no `sku`/`price` column on `products` (a "simple" WooCommerce product's own identifiers), and P2-05 explicitly declined to invent one. This left every simple-product order line permanently unresolvable (confirmed 0% on dev). The project owner decided to add these two columns (new, reversible migration) plus a new resolver step (`CatalogService::resolveProductBySku()`, PRD §10 step "3.5") rather than a synthetic default-variation row. `docs/architecture/sprint-6.md` ("رفع" section).
- **`product_categories.name`/`slug` widened to 255 (from 160/180) — project-owner decision, Sprint 6:** a real Woo category (id 2346) has a 194-char percent-encoded slug that overflowed the old `varchar(180)`. Widened past WordPress's own real `wp_terms.name`/`slug` limit (200) with margin, per explicit instruction (widen, not truncate or skip). `docs/architecture/sprint-6.md` ("رفع بخش اول تصمیم ۳").
- **`daily_metrics.product_revenue`/`shipping_revenue` added (deviates from PRD §09's literal column list) — project-owner decision, Sprint 6 (P6-16):** every revenue-showing page (dashboard, orders, drill/CSV) needed a "goods vs. shipping" breakdown; without pre-aggregated columns, showing it on the dashboard would mean a live re-query of `orders` on every page load (PRD §22's own "dashboard < 1s" requirement rules that out). `product_revenue = Σ(subtotal - discount_total)`, `shipping_revenue = Σ(shipping_total)`, same "realized, not fully refunded" order set `revenue`/`net_revenue` already use. New, reversible migration; `DailyMetricsService::rebuild()` updated; full history rebuilt (745 days) and independently cross-checked exact against a direct `orders` query (0 diff on all 4 revenue columns, same invocation). `docs/architecture/sprint-6.md` ("P6-16").
- **Woo's decimal-formatted `price` string accepted, scoped to `ProductDto::price` only — project-owner decision, Sprint 6:** a real Woo product sends `price: "159990.0"`, which the pre-existing, deliberately strict `PayloadReader::toman()` rejects. Rather than loosen `toman()`/`nullableMoney()` everywhere (orders, variations), a separate `nullableDecimalMoney()` path was added and wired into `ProductMapper::map()` alone; a non-zero fraction still fails. `docs/architecture/sprint-6.md` ("رفع بخش دوم تصمیم ۳").
- **An invalid product never stops the whole catalog sync — project-owner decision, Sprint 6:** mirrors the existing Orders rule ("an unresolvable product never rejects an order," `.claude/rules/sync.md`). `CatalogService::tryUpsertProduct()` returns a `CatalogUpsertOutcome` instead of throwing, so Sync never has to import Catalog's Exceptions to react to a conflict — the module boundary (CLAUDE.md §1) stays exactly as strict as before. `docs/architecture/sprint-6.md` ("رفع بخش دوم تصمیم ۳").
- **Dashboard (P6-06): "Active segments"/"system health" widgets are link-out cards, not inline data — reasoned default, not a PRD instruction.** PRD §18's own widget list names both, but PRD §07's module dependency table gives Analytics only `[Core, Orders, Metrics, Catalog]` — no Segments, no Sync. Duplicating either module's query inside Analytics, or adding either as a new Analytics dependency, would be an undocumented architecture change; instead both render as a plain link to their existing page (`/segments`, `/system/health`), gated by the already-shared `useCan()` client permission check — no new backend read. "AI summary" is omitted outright (Sprint 7/AI Analyst not started, no real data exists). Only KPIs/trend/new-vs-returning are period-scoped — RFM/churn/cohort/affinity read tables with no date dimension of their own, so the period filter does not apply to them. "ارزش در خطر" (value at risk) has no PRD formula; implemented as `SUM(COALESCE(clv_estimated, clv_historical))` over high/lost-risk customers — a reasoned default. No charting library exists in this codebase (checked `package.json`); the dashboard's "trend" widget is a table, matching the existing RFM page's own no-chart convention, not a new dependency added unilaterally. `docs/architecture/sprint-6.md` ("P6-06").
- **Drill-down (P6-07) scoped to 5 widgets, not "every number" literally — reasoned default, PRD gives one boxed technical detail (`GET /internal/drill/{widget}`) and one prose sentence, nothing else.** `orders` (backs orders_count/net_revenue/aov together — same underlying row set), `customers_new`, `customers_repeat`, `rfm_segment`, `churn_level`. Cohort-cell and affinity-pair drill are explicitly NOT built: unlike the five above, they need real re-derivation (which customers were active in a specific cohort/period cell; which customers co-bought a specific stored pair), not a simple filtered list — a materially larger scope, deferred as an Open Item, not guessed at. Export reuses `customers.export` (not a new `dashboard.export`/`analytics.export` permission) — same precedent already set by `SegmentService::export()` ("the same audited PII release as any other customer export"). JSON drill rows are PII-minimal (id + numbers only, same rule `RfmPageService::topChampions()` already applies); only the audited CSV export may include name/phone. `docs/architecture/sprint-6.md` ("P6-07").
- **Cohort/Retention/Affinity pages (P6-08) gated by `analytics.view`, not `dashboard.view` or `metrics.view` — reasoned default, PRD assigns no permission per page.** `analytics.view` was already seeded (Sprint 6 start) and mapped to the Viewer role, but until this task no route actually used it — PRD §07's own module table names `AnalyticsService`/`CohortService`/`AffinityService` under "Analytics", making this the natural fit, not `metrics.view` (a different module) or `dashboard.view` (a different page). `RetentionService::summary()`'s three N-day windows (7/30/90) are a reasoned default too — PRD §15 gives no fixed list (only the Affinity table has explicit per-level minimums). `docs/architecture/sprint-6.md` ("P6-08").
- **Nightly chain (P6-09) — PRD §22 is explicit about failure handling, not silent: native `Bus::chain` stop-at-first-failure is used as-is.** PRD's own words: "ترتیب حیاتی است. `Bus::chain` در اولین شکست متوقف می‌شود — بهتر است چیزی اجرا نشود تا با داده ناقص اجرا شود." A failed step's exception is logged (`->catch()`) but the rest of the chain is skipped, not run anyway — this is a case of PRD not being silent, so no default was needed. `hm:nightly-chain` (`app/Console/Commands`) is the only place in this codebase that imports Jobs across Sync/Metrics/Analytics/Segments in one file — allowed because the module-dependency arch test scans only `app/Modules/**`, and a Job's whole purpose (unlike a Model/Enum/Exception) is to be dispatched from outside its module. PRD §22's "Customers" chain step has no job of its own: customer identity is resolved as a side effect of Orders ingestion (`CustomerIdentityService`, called from `OrderSyncService`), not a separate Woo customers-endpoint pull — `SyncEntity` has no `Customers` case (its own docblock already says so: "customers are not run through here yet"). "ReconcileJob(2)" is read as "the last 2 complete Jalali months" (new `ReconciliationMonths::lastN()`/`ReconciliationService::dispatchRecentMonths()`/`ReconcileRecentMonthsJob`) — a cheap nightly re-check, not `hm:reconcile --all`'s full history, which stays available unscheduled. `GenerateDailyBriefJob`/`GenerateWeeklyReviewJob`/`PruneLogsJob`/`HealthCheckJob`/`backup:run`/`horizon:snapshot` were not built at this point — the last two named here were built in P6-10 (below); see Open Items for the remaining four. `docs/architecture/sprint-6.md` ("P6-09").
- **Alerts + log pruning (P6-10) — `HealthCheckService` (new) lives in `app/Support`, not any module: it composes Sync + Metrics + Core, and no module's PRD §07 dependency table covers all three at once.** Same reasoning as `NightlyChainCommand` (P6-09) — the arch test enforcing "only reach another module through Services/Events" scans only `app/Modules/**`, so `App\Support` is the one architecturally valid home. All 5 wired alert conditions (`SyncFailure`, `MetricRunFailure`, `ReconciliationVariance`, `FailedJobsThreshold`, `NightlyChainTimeout`) reuse the existing `AlertService`/`SettingKey` thresholds from P0-09 exactly as they already existed (no new alert mechanism, no new Settings). `AiBudgetThreshold` (the 6th `AlertKind` case) is deliberately NOT wired — `BudgetGuard`/the AI module do not exist yet (Sprint 7) — see Open Items. `PruneLogsJob` prunes only `sync_logs` (`SyncService::pruneLogs()`, chunked deletes), never `audit_logs` — a reasoned default: PRD names no retention window for either table, but CLAUDE.md §21's own Backup section explicitly lists "audit logs" as NOT recoverable from Woo (the reason backup exists at all), so pruning them was judged out of scope without an explicit instruction; `sync_logs` is pure operational/debug noise with no such protection. Retention is `config('woo.sync_log_retention_days')` = 30 (reasoned default matching PRD §21's own 30-day backup retention — PRD names the job but never a window). `ReconciliationVariance`'s alert threshold (`SettingKey::AlertsReconciliationDiffPercent`, default 1.0, configurable) is deliberately independent of GATE 1's own fixed 1% red/green boundary (`RevenueVariance`, hardcoded, PRD §11) — they answer different questions (an ops alert threshold an admin may tune vs. the hard sprint gate) and were kept that way rather than merged. `SyncService::ordersConsecutiveFailures()` (not `SyncHealthService`, where it was first tried) — `SystemPagesBoundaryTest` enforces a P2-12 rule that the Health page's read path never references a Cursor at all, even a harmless column on it; a new Health-page-adjacent read belongs on `SyncService` (which already owns the whole `SyncCursor` lifecycle), never on `SyncHealthService`. `docs/architecture/sprint-6.md` ("P6-10").
- **Jalali date unification (P6-11) — three genuinely inconsistent decisions, resolved rather than guessed at.** Time format stays `HH:mm:ss` (the existing, already-far-reaching `App\Support\TehranDateTime::format()`), not the `HH:mm` first asked for — changing the shared util would have touched every already-correct page (Customer 360, RFM, Segments, Health, Sync Logs, Identity Conflicts), a much bigger, unrelated change. Digits stay ASCII (`JalaliDate::format()`'s own output), not Persian numerals, for the same "one already-consistent source" reason. CSV export date columns: PRD/CLAUDE.md are silent, so they follow the same in-app rule — Jalali, via the identical backend conversion. `docs/architecture/sprint-6.md` ("P6-11").
- **4 UI fixes before stats sign-off (P6-12) — the real root cause of every Persian digit was `toLocaleString('fa-IR')` (`formatNumber()`, plus 4 scattered direct calls bypassing it), not a font or a locale file; the Arabic percent-sign glyph (٪) was a separate, second root cause (3 pages had byte-for-byte duplicated local `percentText()` helpers).** Both eliminated at the source: `formatNumber()`/`formatToman()` now call `'en-US'` (Latin digits, comma grouping — the same `Intl` machinery, only the locale changed); new `formatPercent()`/`formatRate()` replace all 3 duplicates plus 2 other pages' own percent helpers. A real backend instance was also found and fixed: `CustomerNotesService`'s validation message had Persian digits hardcoded into it. Drill-down header labels are two separate tables by necessity, not an oversight — `DrillService::COLUMN_LABELS` (PHP, the literal CSV header row text) and `resources/js/lib/drill-labels.ts` (TS, display-only text layered over the JSON endpoint's intentionally-English `columns` keys, which `DrillDialog` still needs as `row[column]` data keys) — kept in sync by hand since the two run in different languages. Sidebar collapse/trigger/keyboard-shortcut/cookie-persistence were all found already fully implemented by the existing shadcn `ui/sidebar.tsx` primitive and `HandleInertiaRequests.php`'s matching cookie read — no code changed there. `min-w-0` was added to `Card`/`CardContent` (not per-page) because every page's wide table already sits inside one, and `Table` itself already self-wraps in `overflow-x-auto` — the missing piece was letting that wrapper actually shrink below its content's natural width inside the page's own flex-col chain. `docs/architecture/sprint-6.md` ("P6-12").
- **RFM's "M" can score from a 60-day window instead of lifetime `monetary` (deviates from PRD §12's lifetime-NTILE formula) — project-owner decision, P6-20:** 3 years of Toman inflation makes a lifetime-NTILE M compare a 1403 order against a 1405 one at face value. New `config('metrics.monetary.mode')` ('lifetime', default, byte-identical to PRD §12 and GATE 2 — the old `RfmCalculator::scoreEligible()` SQL is untouched; or 'recent_window', scoring from the new nullable `customer_metrics.monetary_recent` column instead, cut-points computed from that window's own log-median/MAD distribution — the same 4 z-score cuts [-0.84,-0.25,0.25,0.84] that split a normal distribution into quintiles, chosen over NTILE specifically because it is unmoved by one extreme outlier and gives equal amounts equal scores, where NTILE's rank-based buckets would not). **Read-only impact simulation on dev (14,290 RFM-eligible customers, not applied):** every segment except `cant_lose`/`lost` is byte-identical under either mode (PRD §12's segment CASE only references `m_score` in the `cant_lose` condition) — `cant_lose` collapses from 5→0 customers, `lost` grows 14→19, because a `r_score=1` customer (long since ordered) is structurally very unlikely to also have a purchase in the last 60 days, so `m_score` is forced to 1 and `cant_lose`'s `m_score>=4` requirement can almost never be met. 82.9% of eligible customers (11,841/14,290) have no realized purchase in the window at all. Two fixes proposed, neither applied: reference a non-windowed value (e.g. `clv_historical`) in `cant_lose`'s own condition, or add a separate win-back segment independent of windowed M — a PRD/product decision, not something to apply silently. `docs/architecture/sprint-6.md` ("P6-20") has the full before/after table, cut-point edges, and a PRD §12 patch-text proposal (PRD.md itself was not edited).
- **Currency: Toman (IRT), int, no decimals** (bigint). Woo API already returns Toman — verified against a real order amount. Never floats for money (CLAUDE.md §2).
- **`realized_statuses = ['processing', 'completed']`** — `shipped` does not exist in this store's data; never hardcode elsewhere, always `config('woo.realized_statuses')`.
- **Guest checkout: disabled store-wide.** Every order has a `customer_id`; the `woo_guest_order` path is dead code.
- **Phone: 100% present** on orders (0% guest, 0% phone-less in the P0-00 sample) — identity keys off phone with no fallback. (Sync later surfaced a small real phone-less rate — see Open Items.)
- **Refunds carry `line_items`** — refund is computed at line-item level, not order level.
- **Email: ~0.3% coverage** — never used even as a secondary identity signal.
- **DB connection timezone: `UTC`, hardcoded** in `config/database.php`'s `pgsql` connection (not `.env` — an architectural constant, not an environment setting). Local Postgres defaults to `Asia/Tehran`; without this, every `timestamptz` write silently shifted 3.5 hours (found in P0-05, see `docs/architecture/sprint-0.md`). `to_jalali*()` PL/pgSQL functions (P0-04) are unaffected — they use explicit `AT TIME ZONE 'Asia/Tehran'`.
- **Permissions: deny > allow (override) > role > default-deny**, enforced in both middleware and service layer (P0-07). This is why Spatie was rejected — no first-class deny override.
- **Segments module: raw SQL banned outright** (arch-test enforced); `app/` broadly bans raw SQL except the Metrics/Analytics modules and one documented, named استثنای Rule 7 (Rule 7 exception) in Catalog's `ProductListService` (P3-07: a store-wide grouped SUM/COUNT/MAX with no query-builder form) — see `docs/architecture/sprint-3.md` for the full reasoning; this line is what `tests/Arch/CatalogBoundaryTest.php` checks for.
